# Supabase — تشغيل المخطط

| الملف | الغرض |
|---|---|
| [`0001_govmind_supabase.sql`](0001_govmind_supabase.sql) | الجداول العشرة، وسياسات RLS، واختبارات العزل. **ملف واحد يُنفَّذ كما هو.** |
| [`0002_installation_sessions.sql`](0002_installation_sessions.sql) | رموز التركيب لمرة واحدة، والاستهلاك الذرّي. |
| [`0003_registration.sql`](0003_registration.sql) | تسجيل حساب فردي مع اشتراكه التجريبي. |
| [`0004_device_replacement.sql`](0004_device_replacement.sql) | استبدال الجهاز ذاتيًا، بلا مسؤول يوافق. |
| [`0005_device_credentials.sql`](0005_device_credentials.sql) | **بيان اعتماد الجهاز**: يصدره السيرفر، ويُخزَّن مجزّأً، ويُبطل مع الجهاز. |

**تُنفَّذ بالترتيب.** كل ملف يبدأ بفحص أوّلي يرفض التنفيذ إن نقص ما قبله،
وينتهي باختبارات تُفشل الهجرة إن اختلّ شرط أمني.

⚠️ **لا يُعدَّل ملف هجرة نُفّذ على قاعدة حيّة.** التغيير يأتي في ملف جديد
بعده؛ تعديلُ القديم يجعل ما في القاعدة يختلف عمّا في المستودع بلا أثر.

> Oracle ومخزن الذاكرة **باقيان كما هما**. Supabase مزوّد بيانات ثالث
> يُختار بـ`DATA_STORE=supabase`، ولا يستبدل شيئًا.

## ١. التشغيل

1. افتح مشروعك في Supabase ← **SQL Editor** ← **New query**.
2. الصق محتوى `0001_govmind_supabase.sql` كاملًا.
3. اضغط **Run**.
4. كرّر الخطوتين ٢ و٣ لكل ملف بعده **بالترتيب**: `0002` ثم `0003` ثم
   `0004` ثم `0005`.

### الهجرة ٥ — بيان اعتماد الجهاز

هذه أحدث هجرة، وهي **إلزامية** لهذا الإصدار: بدونها يفشل استبدال جلسة
التركيب بـ`404` من دالة قاعدة غير موجودة، فيبقى الجهاز غير مربوط.

ما تضيفه: جدول `device_credentials`، ومشغّلًا يبطل بيان الاعتماد لحظةَ
إبطال تفعيله، ودالتَي إصدار ومصادقة، ودالة تنظيف. وتنتهي باثني عشر
اختبارًا تغطّي التدوير، واستبدال الجهاز، والاشتراك المنتهي والموقوف
والملغى، وعزل القراءة عن العملاء، وانحدار التنظيف.

عند النجاح ترى:

```
NOTICE:  GovMind: بدء اختبارات بيان اعتماد الجهاز…
NOTICE:  GovMind: اجتازت اختبارات بيان اعتماد الجهاز الاثنا عشر ✔
NOTICE:  GovMind: اجتاز اختبار انحدار تنظيف بيانات الاعتماد ✔
NOTICE:  GovMind: اكتملت الهجرة ٥ — بيانات اعتماد الجهاز جاهزة.
```

**بعد التنفيذ يجب أن يعيد كل عميل ربط جهازه من الإضافة مرة واحدة.** أجهزةٌ
مفعَّلة قبل هذه الهجرة لا بيان اعتماد لها، فيعرض لها الـRuntime «بانتظار
ربط هذا الجهاز» — والربط لا يستهلك مقعدًا جديدًا ولا يبطل تفعيلها، لأن
هويّة الجهاز نفسها تبقى ويكون الاستبدال مُعادَ التنفيذ.

الملف ينتهي بكتلة اختبارات تزرع جهتين وثلاثة مستخدمين، وتنتحل هوية كلٍّ
منهم عبر `set local role authenticated`، وتتحقق من ثمانية شروط عزل، ثم
تحذف كل ما زرعته. **فشل أي تأكيد يرفع استثناءً فتتراجع الهجرة كلها** — لا
يمكن أن يبقى في مشروعك مخطط ثبت تسريبه.

عند النجاح ترى في السجل:

```
NOTICE:  GovMind: تنفيذ أول — لا جداول سابقة.
NOTICE:  GovMind: بدء اختبارات العزل...
NOTICE:  GovMind: اجتازت اختبارات العزل الثمانية جميعها ✔
NOTICE:  GovMind: اجتاز اختبار انحدار التنظيف — لا صفوف باقية ✔
```

### إعادة التنفيذ آمنة

الملف **تحديثي (idempotent)**: كل `create` بـ`if not exists`، وكل سياسة
تُحذف قبل إنشائها، وكل دالة `create or replace`. تشغيله مرة ثانية لا يكسر
شيئًا ولا يمسّ أي بيانات إنتاج.

يبدأ بفحص أوّلي **لا يغيّر شيئًا**، يخبرك بحالة القاعدة قبل أن يعمل:

```
NOTICE:  GovMind: الجداول موجودة — هذا التنفيذ تحديثي (idempotent).
NOTICE:  GovMind: لا بقايا اختبار — المحاولة السابقة تراجعت بالكامل.
```

أو، إن كانت محاولة سابقة قد توقّفت في منتصفها وخلّفت أثرًا:

```
NOTICE:  GovMind: بقايا من تنفيذ سابق لم يكتمل (2 جهة اختبار، 3 حساب اختبار). ستُنظَّف قبل الزرع.
```

**البقايا تُنظَّف تلقائيًا قبل الزرع من جديد**، فلا تحتاج سكربت إصلاح
منفصلًا. صفوف الاختبار لها معرّفات ثابتة معلومة — جهتان بـ`slug` يبدأ
بـ`rls-test-org-`، وثلاثة حسابات على `@govmind.test` بمعرّفات `uuid` ثابتة
— ولا يُحذف أي صف خارج هذا النطاق.

### ترتيب حذف صفوف الاختبار

`profiles.organization_id` مفتاح أجنبي بـ`on delete restrict` **عمدًا**:
جهة ما زال فيها موظفون لا تُحذف بالخطأ. لذلك ينظّف الملف من الابن إلى الأب:

```
file_chunks → files → messages → conversations → audit_logs
  → device_activations → subscriptions → organization_members
  → profiles → organizations → auth.users
```

كتلة انحدار في آخر الملف تثبت الأمرين معًا: أن دورة زرع/تنظيف كاملة تمرّ بلا
`23503`، وأن القيد **ما زال** `RESTRICT` — فلا يُصلَح الترتيب بإضعاف القيد.

## ١-١. تجربة الملف محليًا قبل التنفيذ على مشروع حقيقي

يمكن تشغيل الملف كاملًا على PostgreSQL مؤقّت بلا حساب Supabase ولا شبكة.
يحتاج Python 3.12 (حزمة `pgserver` لا تبني على 3.13 بعد):

```bash
uv venv /tmp/pgvenv --python 3.12
uv pip install --python /tmp/pgvenv/Scripts/python.exe pgserver
```

ثم هيّئ ما توفّره Supabase وليس في PostgreSQL العادي — مخطط `auth` وجدول
`auth.users` ودالة `auth.uid()` التي تقرأ `request.jwt.claims`، ودورَي
`anon` و `authenticated` بلا `BYPASSRLS` — ونفّذ الملف مرتين للتأكد من أنه
تحديثي. كل الفشل يظهر كسطر `ERROR:` في المخرجات.

> **افعل هذا قبل كل تنفيذ حيّ.** خطأ `23503` الذي ظهر في أول تنفيذ حيّ كان
> سيظهر هنا في ثوانٍ.

## ٢. تجهيز أول جهة وأول مسؤول

**لا يُنشأ شيء من هذا تلقائيًا**، وجهة بلا صف اشتراك ممنوعة من الخدمة
عمدًا (فشل مغلق).

```sql
-- ١) الجهة
insert into public.organizations (name, slug)
values ('اسم الجهة', 'org-slug')
returning id;

-- ٢) الحساب: من Dashboard ← Authentication ← Add user، ثم انسخ الـuuid.

-- ٣) الملف والعضوية والاشتراك
insert into public.profiles (id, organization_id, email, full_name, role)
values ('<uuid>', <org_id>, 'admin@org.gov.sa', 'اسم المسؤول', 'admin');

insert into public.organization_members (organization_id, user_id, role)
values (<org_id>, '<uuid>', 'admin');

insert into public.subscriptions (organization_id, status, seats, expires_at)
values (<org_id>, 'trial', 10, now() + interval '30 days');
```

## ٣. إدارة الأجهزة

كل اشتراك يعمل على **جهاز واحد**، يفرضه فهرس فريد جزئي لا فحصٌ في الكود.

```sql
-- أجهزة اشتراك جهة
select d.id, d.device_name, d.activated_at, d.last_seen_at, d.revoked_at
from public.device_activations d
join public.subscriptions s on s.id = d.subscription_id
where s.organization_id = <org_id>
order by d.activated_at desc;

-- إبطال تفعيل ليتمكّن العميل من تفعيل جهاز بديل
update public.device_activations set revoked_at = now() where id = <id>;
```

الصف **لا يُحذف**: تاريخ الأجهزة جزء من سجل الاشتراك، وملء `revoked_at`
يخرجه من الفهرس الجزئي فيصير المكان شاغرًا.

المسؤول يستطيع فعل الأمرين من الـAPI كذلك:
`GET /api/account/devices` و `POST /api/account/devices/{id}/revoke`.

## ٤. المفاتيح

| المفتاح | أين يوضع | لماذا |
|---|---|---|
| `anon` | الـBackend فقط (`SUPABASE_ANON_KEY`) | تسجيل الدخول. ليس سرًّا بطبيعته. |
| `service_role` | **الـBackend وحده** (`SUPABASE_SERVICE_ROLE_KEY`) | يتجاوز RLS بالكامل. |
| `JWT Secret` | الـBackend (`SUPABASE_JWT_SECRET`) | التحقق من رموز المستخدمين محليًا. |

> ⚠️ **`service_role` لا يوضع في الواجهة ولا في إضافة المتصفح إطلاقًا.**
> هو يتجاوز كل سياسات هذا الملف، فوجوده في العميل يُلغي العزل كله.
> الإضافة لا تعرف عنوان Supabase أصلًا: كل طلباتها تمرّ بالـBackend.

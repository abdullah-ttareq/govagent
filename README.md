# GovMind

مساعد ذكاء اصطناعي عام لموظفي الجهات الحكومية. الجهة تثبّت النظام على سيرفرها،
ويتصل موظفوها بتطبيق ويب قابل للتثبيت كـPWA، أو بإضافة متصفح خفيفة.

جميع الموظفين يستخدمون نفس الإيجنت العام. الفرق بينهم في الحسابات والمحادثات
والملفات والصلاحيات فقط.

> **هذا مشروع تخرج في مرحلة MVP، وليس نظامًا جاهزًا للإنتاج.**
> لا تُستخدم فيه بيانات حكومية حقيقية ولا بيانات اعتماد حقيقية.

---

## عرض أكاديمي: الاستدلال السحابي عبر LiveKit

⚠️ **في هذا العرض لا تبقى المحادثة على جهاز المستخدم.** حين يُبنى المثبّت
بـ`-ChatMode cloud`، يمرّ نصّ المحادثة من التطبيق المثبَّت إلى الـRuntime
المحلي، ثم إلى الـBackend المستضاف، ثم إلى **LiveKit Cloud Inference**.
والتطبيق يعلن ذلك صراحةً في واجهته قبل أن يكتب المستخدم أول حرف.

المسار: `التطبيق المثبَّت ← Runtime (127.0.0.1) ← Backend ← LiveKit`.

**لماذا يمرّ الطلب بالـBackend بدل أن ينادي الجهاز المزوّد مباشرة؟** لأن
مفتاح المزوّد سرّ سيرفر؛ وضعُه على جهاز عميل يعني نشره. فالجهاز يصادق
ببيان اعتماده هو (ترويسة `X-GovMind-Device-Credential`)، والسيرفر يحمل
المفتاح ولا يخرجه. ولا يصل بيان الاعتماد إلى شيفرة المتصفح إطلاقًا.

المسار الوحيد المضاف إلى قائمة الـRuntime البيضاء لهذا الغرض هو
`POST /api/runtime/chat`.

**متغيّرات البيئة المطلوبة — الأسماء فقط، ولا تُكتب قيمها في المستودع:**

```
MODEL_PROVIDER=livekit
LIVEKIT_URL
LIVEKIT_API_KEY
LIVEKIT_API_SECRET
LIVEKIT_MODEL
```

تُقرأ من `.env` على السيرفر وحده. **لا يصل أيٌّ منها إلى الواجهة ولا إلى
الإضافة ولا إلى حزمة المثبّت** — ويحرس ذلك فحصٌ في `installer/build.ps1`.

## ٤. تشغيل الإضافة (Extension)

إضافة متصفح **Manifest V3** بـHTML و CSS و JavaScript مباشر — بلا React وبلا
Build System، وبلا Content Scripts، وبلا أي صلاحية لقراءة صفحات المستخدم.

⚠️ **لم تعد واجهة محادثة.** منذ الإصدار 0.3.0 مهمتها واحدة: تجهيز GovMind
على جهاز العميل — دخول، فحص اشتراك، تفعيل الجهاز، تنزيل المثبّت. المحادثة
تحدث في تطبيق GovMind على الجهاز لا في المتصفح.

1. شغّل الـBackend أولًا (الخطوة ١ أعلاه).
2. افتح `chrome://extensions` في Chrome أو Edge.
3. فعّل **Developer mode**.
4. اضغط **Load unpacked** واختر مجلد `extension`.
5. اضغط أيقونة GovMind واتبع الخطوات.

**لا يُدخل المستخدم رابطًا ولا عنوان سيرفر ولا مفتاح API في أي شاشة.**
العنوان ثابت وقت البناء في `extension/config.js`، ويجب أن يطابق
`host_permissions` في `extension/manifest.json` — القيمتان تُغيَّران معًا.

التفاصيل الكاملة في [`extension/README.md`](extension/README.md).

## المصادقة (تسجيل الدخول)

| المسار                  | الوصف                                     |
| ----------------------- | ----------------------------------------- |
| `POST /api/auth/login`  | يعيد رمز دخول (JWT) وبيانات الموظف         |
| `GET /api/auth/me`      | بيانات الحساب الحالي — **محمي**            |
| `POST /api/auth/logout` | تأكيد الخروج — **محمي**                    |

الرمز يُرسل في كل طلب محمي بترويسة `Authorization: Bearer <token>`، أو يُلصق في
زر **Authorize** في <http://localhost:8000/docs>.

الرمز يحمل `user_id` و `organization_id` و `role`، ومدته ٨ ساعات. **الجهة تُقرأ
من الرمز دائمًا ولا تُقبل من جسم الطلب**، وهو أساس عزل البيانات بين الجهات.

### مستخدمو التطوير

بـ`DATA_STORE=memory` (الافتراضي) يعمل تسجيل الدخول **بلا قاعدة بيانات**، بمخزن
داخل الذاكرة مزروع بالجهات الثلاث في
[`mock-data/organizations.json`](mock-data/organizations.json) — **بالحالات
نفسها حرفيًا**. كلمة المرور للجميع هي قيمة `DEV_SEED_PASSWORD` في `.env`:

| البريد                             | الدور    | الجهة                | الاشتراك |
| ---------------------------------- | -------- | -------------------- | -------- |
| `admin@digital-services.test`      | admin    | هيئة الخدمات الرقمية   | فعّال    |
| `n.alharbi@digital-services.test`  | employee | هيئة الخدمات الرقمية   | فعّال    |
| `f.alqahtani@digital-services.test`| employee | هيئة الخدمات الرقمية   | فعّال    |
| `admin@urban-planning.test`        | admin    | مركز التخطيط العمراني  | فعّال    |
| `l.aldosari@urban-planning.test`   | employee | مركز التخطيط العمراني  | فعّال    |
| `admin@national-archive.test`      | admin    | هيئة الأرشيف الوطني    | **منتهٍ** |
| `r.alanzi@national-archive.test`   | employee | هيئة الأرشيف الوطني    | **منتهٍ** |

**جهتان فعّالتان وثالثة منتهية عمدًا:** الفعّالتان تُثبتان عزل البيانات — ولا
يمكن إثباته بجهة لا يُسجَّل الدخول إليها — والثالثة تُختبر بها رسالة انتهاء
الاشتراك. حساب `s.alzahrani@urban-planning.test` معطّل عمدًا كذلك.

تسجيل الدخول بحساب من الجهة الثالثة يعيد **403** برسالة الانتهاء الفعلية —
انظر [فحص الاشتراك](#فحص-الاشتراك).

> المخزن **غير دائم** ويفرغ عند إعادة التشغيل — للتطوير والعرض لا للإنتاج.
> على السيرفر: `DATA_STORE=oracle` لقراءة الجهات والمستخدمين من القاعدة.

## الجهات والمستخدمون

| المسار                             | الوصف                          | من يستطيع              |
| ---------------------------------- | ------------------------------ | ---------------------- |
| `POST /api/organizations`          | تجهيز جهة جديدة ومسؤولها الأول | مفتاح التجهيز — إلزامي |
| `GET /api/organizations/{id}`      | قراءة بيانات الجهة             | أي موظف — جهته فقط     |
| `PATCH /api/organizations/{id}`    | تعديل اسم الجهة أو معرّفها      | مسؤول الجهة            |
| `GET /api/users`                   | قائمة موظفي الجهة              | مسؤول الجهة            |
| `POST /api/users`                  | إضافة موظف                     | مسؤول الجهة            |
| `GET /api/users/{id}`              | قراءة بيانات موظف              | مسؤول: أي موظف في جهته · موظف: نفسه |
| `PATCH /api/users/{id}`            | تعديل بيانات موظف              | مسؤول: الكل · موظف: اسمه وكلمة مروره |
| `DELETE /api/users/{id}`           | **تعطيل** حساب موظف            | مسؤول الجهة            |

### عزل البيانات بين الجهات

**`organization_id` لا يوجد في أي طلب.** الجهة تُشتق من رمز الدخول وحده، في
[`directory_service.py`](backend/app/services/directory_service.py). أي محاولة
للوصول إلى سجل جهة أخرى تعيد **404 بلا بيانات** — لا 403، لأن «ممنوع» تؤكد أن
السجل موجود وهذه معلومة عن جهة أخرى.

الإثبات في [`tests/test_isolation.py`](backend/tests/test_isolation.py)، ومنه
اختبار يفحص مواصفة OpenAPI كلها فيفشل لو أعاد أحدٌ الحقل إلى أي طلب مستقبلًا.

### البريد هوية دخول فريدة على مستوى النظام

تسجيل الدخول يبحث بالبريد **قبل** أن تُعرف الجهة — لا توجد هوية موثوقة بعد.
لو تكرر البريد بين جهتين لصار على النظام أن يخمّن أيهما، وهذا ما لا يجوز في
نظام قائم على عزل الجهات.

لذلك البريد فريد على مستوى النظام كله، **بحروف غير حسّاسة** (`Ahmad@x` و
`ahmad@x` بريد واحد)، يفرضه فهرس `uq_users_email_lower` في
[`schema.sql`](database/schema.sql) وفحصٌ مقابل في مخزن الذاكرة. بريد مستخدم
في أي جهة يُرفض بـ409 عند إضافة موظف أو تجهيز جهة.

نتيجته أن `POST /api/auth/login` **لا يطلب معرّف جهة**: البحث بالبريد يعطي
حسابًا واحدًا أو لا شيء. ولو حملت قاعدة قديمة (سبقت الفهرس) بريدًا مكررًا،
**يُرفض الدخول بـ409** ولا يُختار أحد الحسابين — لا يوجد في المشروع مسار
يختار «أول مستخدم».

> **`POST /api/chat` والجهة:** كان المسار يقبل `organization_id` في جسم
> الطلب وبلا مصادقة، فيستطيع أي أحد قراءة مقاطع ملفات أي جهة برقم واحد.
> الحقل **حُذف** في P2-02، وصار المسار **محميًا بالكامل** في P4-03:
> الجهة تُقرأ من رمز الدخول وحده، ولا يوجد حقل يقابلها في أي طلب.

### تجهيز جهة جديدة

إنشاء الجهة عملية **تركيب** يقوم بها من ينشر النظام، لا عملية داخل التطبيق: لا
يوجد مستخدم في الجهة الجديدة ليأذن بها. لذلك يحرسها `PROVISIONING_KEY` في
ترويسة `X-Provisioning-Key` بدل رمز الدخول، وتُنشئ الجهة ومسؤولها الأول معًا
لأن جهة بلا مسؤول لا يمكن الدخول إليها.

> **`PROVISIONING_KEY` إلزامي في كل البيئات، بلا استثناء للتطوير.** تركه
> فارغًا **يعطّل المسار** ويعيد 503، ولا يجعله مفتوحًا — والمفتاح الفارغ لا
> يُقارَن بترويسة أصلًا، فلا تطابقه ترويسة فارغة. بيئة تطوير مكشوفة على
> الشبكة، أو `APP_ENV` منسيّة على قيمتها الافتراضية عند النشر، كانت تكفي
> لجعله بابًا مفتوحًا لو استُثنيت. التطوير المحلي لا يحتاجه أصلًا: مخزن
> الذاكرة مزروع بجهتين جاهزتين.

```bash
curl -X POST http://localhost:8000/api/organizations \
  -H "Content-Type: application/json" \
  -H "X-Provisioning-Key: $PROVISIONING_KEY" \
  -d '{"name":"وزارة التجربة","slug":"test-ministry","admin_email":"admin@test-ministry.test","admin_full_name":"خالد المطيري","admin_password":"ChangeMe@2026"}'
```

**التعطيل بدل الحذف:** `DELETE /api/users/{id}` يضع `is_active = 0` ولا يحذف
الصف — المستخدم مرتبط بمحادثاته وملفاته وسجل تدقيقه، وحذفه يترك تاريخًا بلا
صاحب. الحساب المعطّل يُمنع من الدخول ومن كل مسار محمي، ويُعاد تفعيله بـ`PATCH`.

### `JWT_SECRET`

سر توقيع الرموز. اتركه فارغًا محليًا ليُولَّد عشوائيًا عند كل تشغيل (تسقط الرموز
القديمة عند إعادة التشغيل، وهذا مقبول محليًا). **خارج `APP_ENV=development` هو
إلزامي**، وبدونه تُرفض الطلبات المحمية برسالة واضحة. ولّده بـ:

```bash
python -c "import secrets; print(secrets.token_urlsafe(48))"
```

كلمات المرور تُخزَّن **مُجزّأة بـbcrypt** فقط، ولا تُكتب صريحة في قاعدة ولا سجل
ولا رد.

| `DELETE /api/files/{id}`                    | حذف ملف                   |

**كلها تتطلب رمز دخول.**

### نطاقان مختلفان: المحادثة خاصة، والملف معرفةٌ مشتركة

| المورد | القراءة | التعديل والحذف | جهة أخرى |
| ------ | ------- | -------------- | -------- |
| **المحادثة ورسائلها** | صاحبها فقط — ولو كان الطالب مسؤول الجهة | صاحبها فقط | 404 |
| **الملف وبياناته** | كل موظفي الجهة | رافعه أو مسؤول الجهة | 404 |

**لماذا يختلفان؟** محتوى الملفات متاح لكل موظفي الجهة أصلًا عبر البحث
المتجهي (`search_chunks` مقيّد بالجهة لا بالمالك)، فلو بقيت **بيانات** الملف
خاصة برافعه لظهر في `sources` مصدرٌ يعيد 404 عند الاستعلام عنه — مصدرٌ
مجهول لقارئ الرد. **صلاحية المصدر يجب أن توازي صلاحية محتواه.** المحادثة
بالمقابل ليست معرفة مشتركة بل عمل شخصي، فتبقى خاصة بصاحبها.

رد الملف يحمل `uploaded_by` و `can_modify` لتعرف الواجهة من رفعه وأيّ ملف
تعرض له زر حذف. حقل `conversation_id` **يظهر لرافع الملف وحده**: ارتباط
ملف بمحادثة جزء من خصوصية المحادثة لا من بيانات الملف.

الحذف يزيل السجل **ومقاطعه في البحث ونسخته على القرص** معًا، فلا يبقى
محتوى يُستشهد به من ملف لم يعد موجودًا. لعرض ملفاتك وحدها: `GET
/api/files?uploaded_by=<معرّفك>`.

الإثبات في [`tests/test_isolation.py`](backend/tests/test_isolation.py)، ومنه
اختبار يسأل بحساب زميل ثم يستعلم عن **كل** ملف ورد في `sources` ويشترط
أن يعيد 200 — فيفشل لو عاد التعارض يومًا.

### المحادثة تُحفظ تلقائيًا

`POST /api/chat` **يتطلب رمز دخول دائمًا** (`Authorization: Bearer <token>`):

* بلا `conversation_id` تُفتح محادثة جديدة بعنوان مشتق من أول رسالة، ويُعاد
  معرّفها في الرد لتُستخدم في الرسائل التالية.
* السؤال والرد يُحفظان معًا بالترتيب الصحيح — لا يُحفظ نصف تبادل.
* **الجهة تأتي من الرمز وحده**، وعليها يُقصر البحث في الملفات وحفظ المحادثة.
* **السياق يأتي من الرسائل المحفوظة على السيرفر لا من العميل.** لا يوجد حقل
  `history` في الطلب: سياقٌ يرسله المتصفح يمكن تلفيقه.

الطلب **بلا رمز يعيد 401** بالغلاف العربي الموحّد، ولا يصل المزود ولا يجري
أي بحث — استخدام المودل بلا هوية ولا سجل تدقيق غير مقبول على سيرفر جهة.

> **أُغلق الوضع الانتقالي في P4-03.** كان المسار يقبل الطلبات بلا رمز ليبقى
> قابلًا للتجربة قبل أن تضيف الواجهة والإضافة تسجيل الدخول، وقد أُنجز ذلك في
> P3-01 و P4-01. يحرس الإغلاقَ اختبارٌ يفشل إن عاد أحد `history` إلى
> `ChatRequest` أو أسقط شرط المصادقة عن المسار
> ([`tests/test_chat_protection.py`](backend/tests/test_chat_protection.py)).

الرسائل تُقرأ **من الأقدم إلى الأحدث** مع `limit` و `offset`
(الافتراضي ٥٠، والسقف ٢٠٠ — يُقصّ ما زاد بدل سحب المحادثة كاملة).

### رفع الملفات

الصيغ المدعومة `.pdf` و `.docx` و `.txt`، والحد الأقصى من `UPLOAD_MAX_BYTES`
(١٠ ميجابايت). التجاوز يعيد **413** وغير المدعوم **415**، ولكل منهما رسالة
عربية تشرح السبب والحل.

الملف يُحفظ في `UPLOAD_DIR/<معرّف الجهة>/` **باسم عشوائي**، والاسم الذي أرسله
الموظف يبقى بيانًا وصفيًا في القاعدة فقط: اسم مثل `../../.env` لا يُستخدم في
المسار إطلاقًا. المجلد مُدرَج في `.gitignore`.

بعد الحفظ يُفهرَس محتوى الملف للبحث في محادثات الجهة. **فشل الفهرسة لا يُفشل
الرفع:** الملف يبقى محفوظًا، وحالته `failed`، والسبب في `indexing_error`.

### فحص الاشتراك

يُفحص **عند تسجيل الدخول وعند كل طلب محمي**، لا عند الدخول وحده: رمز يُصدر
قبل الانتهاء بثوانٍ يبقى صالحًا ثماني ساعات، فالفحص عند الدخول وحده يترك
الخدمة مفتوحة يوم عمل كامل بعد انتهاء الرخصة.

الرد **403 برسالة تذكر تاريخ الانتهاء**، لا خطأ عام:

> انتهى اشتراك جهتك بتاريخ 2026-08-09. راجع مسؤول النظام في جهتك لتجديد
> الاشتراك قبل متابعة الاستخدام.

**فشل مغلق:** جهة بلا صف اشتراك تُمنع، لا تُسمح — رخصة غائبة ليست رخصة
مفتوحة. لذلك تجهيز الجهة ينشئ اشتراكها معها.

**حالات البذرة التجريبية** — في مخزن الذاكرة وفي
[`mock-data/organizations.json`](mock-data/organizations.json) على السواء:

| الجهة                | الاشتراك | المقاعد | الانتهاء   |
| -------------------- | -------- | ------- | ---------- |
| هيئة الخدمات الرقمية   | فعّال    | ١٠      | 2030-01-01 |
| مركز التخطيط العمراني  | فعّال    | ٥       | 2030-01-01 |
| هيئة الأرشيف الوطني    | **منتهٍ** | ٥       | 2025-06-30 |

تسجيل الدخول بحساب من الجهة الثالثة يعيد الرسالة الفعلية بتاريخ البذرة:
«انتهى اشتراك جهتك بتاريخ 2025-06-30…». يحرس تواريخ الفعّالتين اختبار يفشل
بوضوح إن اقترب ٢٠٣٠، بدل أن تتعطّل عشرات الاختبارات بلا سبب ظاهر.

ثلاثة مسارات **تعمل ولو انتهى الاشتراك**: `GET /api/auth/me` و
`POST /api/auth/logout` و `GET .../subscription`. لولاها لعرف المسؤول أن شيئًا
ممنوع بلا أن يعرف السبب ولا أن يستطيع الخروج.

**التجديد بمفتاح التجهيز لا برمز الدخول:** تجديد الاشتراك وزيادة المقاعد قرار
من يقدّم الخدمة لا من يستهلكها؛ لو مَلَكَه مسؤول الجهة لمنح نفسه مقاعد بلا حد.

### التراخيص (المقاعد)

المقاعد المستهلَكة = **عدد المستخدمين النشطين**؛ لا يوجد جدول تراخيص منفصل في
الـMVP، فحسابٌ معطَّل لا يشغل مقعدًا. تجاوز الحد يعيد **409** برسالة تذكر
العددين:

> عدد تراخيص جهتك 3، وجميعها مستخدَمة حاليًا (3 من 3). عطّل حساب موظف غير نشط
> أو راجع مسؤول النظام لزيادة عدد التراخيص.

الفحص يشمل **إعادة تفعيل** حساب معطّل كما يشمل الإنشاء: لولا ذلك لأمكن تجاوز
الحد بتعطيل حساب ثم تفعيل غيره.

### مزود المودل لكل جهة

الجهة تختار مزودها، ويُقرأ من القاعدة بدل `MODEL_PROVIDER` **إن وُجد**. جهة لم
تختر شيئًا تعمل بالإعداد العام كما كانت، فلا يتعطّل شيء بإضافة الميزة، وقراءة
الإعداد تعيد المزود **الفعلي** لا حقلًا فارغًا.

**اسم المزود فقط، بلا مفاتيح ولا أسرار:** بيانات اعتماد OCI تبقى في متغيرات
البيئة على السيرفر، خارج القاعدة وخارج المستودع.

### سجل التدقيق

يسجّل: تسجيل الدخول، إنشاء موظف، تعطيل موظف، حذف محادثة، رفع ملف، حذف ملف،
تغيير مزود المودل، تغيير الاشتراك، تجهيز الجهة — بالمستخدم والجهة والوقت.

**سجل إضافة فقط:** لا مسار تعديل ولا حذف، وسجلٌ يمكن تنقيحه لا يصلح دليلًا.
القراءة **لمسؤول الجهة ولجهته وحدها**، مع ترقيم وتصفية على نوع الحدث أو الموظف.

**التسجيل لا يُفشل العملية أبدًا:** تعذُّر كتابة سطر في السجل يجب ألا يمنع
موظفًا من تسجيل الدخول ولا من رفع ملف.

لكنه **لا يمر صامتًا**: يُكتب `WARNING` في سجل التطبيق يذكر نوع الحدث والجهة
ونوع الخطأ. سجل تدقيق يفقد أحداثًا بلا أثر أسوأ من غيابه، لأنه يعطي ثقة لا
يستحقها. **والتحذير بلا بيانات حساسة:** لا يحمل `details` (وفيه بريد الموظف
واسم الملف) ولا نص الاستثناء (وقد يحمل بيانات اتصال القاعدة) — نوع الخطأ
وحده يكفي للتشخيص.

```
WARNING app.services.audit_service: تعذّر حفظ حدث في سجل التدقيق:
action=user_created organization_id=1 error=RuntimeError. العملية الأصلية لم تتأثر.
```

> ⚠️ مخزن السجل في الذاكرة **غير دائم** ويفرغ عند إعادة التشغيل، فلا يصلح
> سجل تدقيق حقيقي. على السيرفر يلزم `DATA_STORE=oracle`.

## مزود المودل

يُختار المزود من متغير واحد في `.env`:

| القيمة     | الوصف                                                   |
| ---------- | ------------------------------------------------------- |
| `mock`     | **الافتراضي.** يعمل بلا Oracle ويعيد ردًا تجريبيًا عامًا لا يذكر مزودًا. |
| `oracle`   | **اختياري** — OCI Generative AI (يحتاج `OCI_*` وهوية OCI على السيرفر). |
| `lmstudio` | **اختياري** — مودل محلي داخل [LM Studio](https://lmstudio.ai) على الجهاز نفسه. |
| `local`    | مودل داخل سيرفر الجهة — واجهة مستقبلية فقط.             |

```env
MODEL_PROVIDER=mock
```

**Mock Provider هو الافتراضي**، والمشروع يعمل به بالكامل بلا أي بيانات اعتماد.
**Oracle AI و LM Studio اختياريان** ولا يحتاجهما أي جزء من التشغيل المحلي.

القيمة غير المدعومة تُنتج رسالة خطأ واضحة تذكر القيم المقبولة.

### LM Studio — مودل محلي لا يخرج منه نص

`MODEL_PROVIDER=lmstudio` يوصل GovMind بمودل محمّل في LM Studio على الجهاز
نفسه. الاتصال HTTP محلي بواجهة متوافقة مع OpenAI، فلا يغادر أي نص الجهاز ولا
يُطلب أي مفتاح API.

**المزود يمر في مسار المحادثة نفسه:** الـRAG والمصادر وعزل الجهات وحفظ
المحادثات تعمل معه كما تعمل مع `mock` و`oracle` تمامًا.

**التشغيل:**

1. ثبّت [LM Studio](https://lmstudio.ai) وافتحه.
2. من تبويب **Discover** ابحث عن `google/gemma-4-e4b` وحمّله.
3. من تبويب **Developer** (أو Local Server) شغّل الخادم على المنفذ `1234`،
   وتأكد أن المودل **محمّل (Loaded)** لا مُنزَّل فقط.
4. تحقق سريعًا: <http://127.0.0.1:1234/v1/models> يجب أن يعيد المودل.
5. في ملف `.env`:

```env
MODEL_PROVIDER=lmstudio
LM_STUDIO_BASE_URL=http://127.0.0.1:1234/v1
LM_STUDIO_MODEL=google/gemma-4-e4b
LM_STUDIO_TIMEOUT_SECONDS=300
LM_STUDIO_MAX_TOKENS=1500
LM_STUDIO_API_KEY=
```

6. شغّل الـBackend والـFrontend كما في القسمين ١ و٢ أعلاه، ثم أرسل رسالة من
   الواجهة. حقل `provider` في الرد يكون `lmstudio`.

**المتغيرات:**

| المتغير                     | الافتراضي                    | ملاحظة                                    |
| --------------------------- | ---------------------------- | ----------------------------------------- |
| `LM_STUDIO_BASE_URL`        | `http://127.0.0.1:1234/v1`   | يُلحق به `/chat/completions` تلقائيًا.     |
| `LM_STUDIO_MODEL`           | `google/gemma-4-e4b`         | كما يظهر المعرّف في LM Studio.            |
| `LM_STUDIO_TIMEOUT_SECONDS` | `300`                        | مهلة الاتصال والتوليد معًا.               |
| `LM_STUDIO_MAX_TOKENS`      | `1500`                       | سقف طول الإجابة — يحكم زمن الانتظار.      |
| `LM_STUDIO_API_KEY`         | فارغ                         | **اختياري** — لا يطلبه LM Studio المحلي.  |

> **المهلة وسقف الإجابة مرتبطان.** زمن التوليد المحلي يتناسب طرديًا مع عدد
> الرموز المولَّدة، فرفع `LM_STUDIO_MAX_TOKENS` بلا رفع
> `LM_STUDIO_TIMEOUT_SECONDS` يعني انتهاء المهلة في منتصف إجابة سليمة.
>
> ⚠️ **إن كان مودلك من مودلات الاستدلال (Reasoning) فارفع السقف.** هذه
> المودلات تستهلك جزءًا كبيرًا من السقف في تفكير داخلي **لا يظهر للمستخدم**
> قبل أن تبدأ الإجابة. قياس فعلي على `google/gemma-4-e4b`: ٥٠٩ رموز استدلال
> قبل أول حرف، فالسقف `512` أعاد إجابة **فارغة**، و`1500` أعاد ردًا كاملًا —
> ولذلك الافتراضي `1500` مع مهلة `300` ثانية.
> يميّز المزود هذه الحالة برسالة تطلب رفع `LM_STUDIO_MAX_TOKENS` بدل رسالة
> «رد غير صالح» العامة.
>
> **جرّب سؤالًا واقعيًا وقِس الزمن قبل تثبيت القيم على سيرفر الجهة.**

> **داخل Docker:** الحاوية لا ترى `127.0.0.1` الخاص بالمضيف. إن كان الـBackend
> يعمل في Docker والـLM Studio على الجهاز، اضبط:
> `LM_STUDIO_BASE_URL=http://host.docker.internal:1234/v1`.
> ومن يشغّل الـBackend مباشرة (بلا Docker) **يترك القيمة الافتراضية كما هي**.

**رسائل الفشل** تصل إلى الموظف كخطأ 503 بالعربية وحدها، بلا traceback ولا
تفاصيل داخلية: التطبيق مغلق أو الخادم المحلي متوقف، المودل غير محمّل، انتهاء
المهلة، رد غير صالح. التفاصيل التقنية (العنوان ورمز الحالة ونوع الخطأ) تُكتب
في سجل الـBackend وحده.

## الأخطاء والتوثيق

### شكل خطأ واحد لكل المسارات

كل خطأ يعيد الغلاف نفسه مهما كان المسار أو الحالة:

```json
{
  "detail": "المستخدم المطلوب غير موجود.",
  "status": 404,
  "code": "not_found",
  "errors": []
}
```

| الحالة | `code` | متى |
| ------ | ------ | --- |
| 400 | `bad_request` | جسم الطلب ليس JSON صالحًا |
| 401 | `unauthorized` | رمز الدخول مفقود أو تالف أو منتهي الصلاحية |
| 403 | `forbidden` | الدور لا يسمح، أو الحساب معطّل، أو اشتراك الجهة منتهٍ |
| 404 | `not_found` | السجل غير موجود **في نطاق صاحب الطلب** |
| 405 | `method_not_allowed` | طريقة غير مسموحة على المسار |
| 409 | `conflict` | بريد مكرر، أو تراخيص مستنفدة |
| 413 | `payload_too_large` | حجم الملف يتجاوز الحد |
| 415 | `unsupported_media_type` | صيغة ملف غير مدعومة |
| 422 | `validation_error` | حقل مرفوض — التفصيل في `errors` |
| 500 | `internal_error` | خطأ غير متوقع |
| 503 | `service_unavailable` | تعذّر الوصول إلى مزود المودل |

`detail` نصٌّ عربي **دائمًا**، ولو كان الخطأ خطأ تحقق: كان FastAPI يعيد قائمة
كائنات في هذا الحقل فيتعذّر على الواجهة عرضه مباشرة. و`code` معرّف ثابت يُبنى
عليه منطق العميل بدل مطابقة نص الرسالة.

### لا تسريب في أي رد

الخطأ الداخلي يعطي رسالة عربية عامة، و**الـStack Trace يبقى في سجل السيرفر
وحده**: لا نوع الاستثناء ولا نصه ولا مسار الملف يخرج في الرد.

كذلك حُذف من رد التحقق حقلا `input` و`ctx` اللذان كان FastAPI يعيدهما: الأول
يعيد الحقل **كما أرسله المستخدم**، فكلمة مرور قصيرة تعود نصًّا صريحًا في جسم
الرد وفي أي سجل يلتقطه.

### توثيق Swagger

<http://localhost:8000/docs> — كل المسارات موصوفة بالعربية، ولنماذج الطلب
والرد الرئيسية أمثلة جاهزة، وشكل الخطأ الموحّد منشور فيها كنموذج
`ErrorResponse`.

للتجربة: سجّل الدخول من `POST /api/auth/login`، ثم الصق `access_token` في زر
**Authorize** أعلى الصفحة، فتعمل بعدها كل المسارات المحمية من الصفحة نفسها.

| `POST /api/account/devices/verify` | هل هذا هو الجهاز المفعّل؟ |
| `GET /api/account/devices` | سجل أجهزة الاشتراك — **لمسؤول الجهة**. |
| `POST /api/account/devices/{id}/revoke` | إبطال تفعيل — **لمسؤول الجهة**. |
| `POST /api/account/installer/download-url` | رابط SAS قصير العمر. |

### جهاز واحد لكل اشتراك

يفرضه **فهرس فريد جزئي في القاعدة** لا فحصٌ في الكود:
`uq_device_activations_one_active on device_activations (subscription_id) where revoked_at is null`.
طلبان متزامنان لتفعيل جهازين ينجح أحدهما ويفشل الآخر بخطأ تفرّد — لا يمكن
أن ينجحا معًا مهما كان توقيتهما.

تغيير الجهاز يحتاج **إبطالًا من مسؤول الجهة**؛ الصف يبقى في السجل ولا
يُحذف، وملء `revoked_at` يخرجه من الفهرس فيصير المكان شاغرًا.

### بصمة الجهاز لا تُخزَّن خامًا أبدًا

يُخزَّن `HMAC-SHA256` لها بمِلح سرّي من `DEVICE_HASH_PEPPER`، ويرفض قيد
`CHECK` في القاعدة أي قيمة ليست ٦٤ خانة ست عشرية. بلا مِلح يتوقّف التفعيل
برسالة إعداد واضحة بدل أن تُخزَّن تجزئة ضعيفة بصمت. والتجزئة نفسها **لا
تخرج في أي رد**.

### رابط التحميل

يُصدره الـBackend **فقط** إذا تحققت الشروط الأربعة معًا: هوية موثوقة،
وحالة `active` أو `trial`، وتاريخ لم ينتهِ، والطلب من **الجهاز المفعّل**.
الرابط SAS بصلاحية قراءة فقط ومدة `DOWNLOAD_LINK_TTL_MINUTES` (١٥ دقيقة).

⚠️ **سلسلة اتصال Azure لا تخرج من السيرفر**، والرابط لا يُعرض للمستخدم:
يمرّ إلى `chrome.downloads` مباشرة.

> **المثبّت نفسه لم يُبنَ بعد في هذه المرحلة.** ما بُني هو مسار التوزيع
> الآمن كاملًا. انظر [`docs/INSTALLER_PLACEHOLDER.md`](docs/INSTALLER_PLACEHOLDER.md).
>
> **وحتى يُبنى GovMind Runtime، يبقى النظام معتمدًا على LM Studio.**

## الاستضافة

**قرار الاستضافة لم يُحسم بعد.** الخيارات المطروحة: Oracle Cloud (OCI)، أو
VPS مستقل، أو سيرفر الجهة نفسها. المقارنة والتوصية النهائية ضمن مهمة **P1-06**.

## تحذير أمني

لا ترفع ملف `.env` ولا أي مفتاح أو بيانات اعتماد إلى المستودع.
`.env.example` فقط هو المسموح رفعه، ويجب أن يبقى بلا قيم حقيقية.

**مفتاحان لا يخرجان من السيرفر إطلاقًا:**

- `SUPABASE_SERVICE_ROLE_KEY` — يتجاوز RLS بالكامل، فوجوده في الواجهة أو
  في الإضافة يُلغي عزل البيانات كله.
- `AZURE_STORAGE_CONNECTION_STRING` — يحمل مفتاح حساب التخزين.

الواجهة والإضافة لا تعرفان عنوان Supabase ولا عنوان Azure أصلًا: كل شيء
يمرّ بالـBackend.

### موارد Azure — تُنشأ يدويًا

لا يُنشئ الكود أي مورد ولا يكتب أي سرّ. أنشئ يدويًا:

1. **حساب تخزين** (Storage account).
2. **حاوية خاصة** (Private — لا Blob ولا Container؛ الوصول العام يُلغي
   فائدة رابط SAS كلها).
3. **مدوّنة** بالاسم الذي يضبطه `AZURE_STORAGE_BLOB_NAME`.

ثم املأ `AZURE_STORAGE_*` في `.env` على السيرفر.

# GovMind Runtime — المعمارية وحدود الثقة

> **يُقرأ قبل الشيفرة.** هذا المستند يثبّت القرارات التي تُبنى عليها المرحلة
> الثانية: من يملك أي سرّ، ومن يثق بمن، وأين تنتهي صلاحية كل طرف.

---

## ١. لماذا تغيّرت هوية الجهاز

في المرحلة الأولى كانت بصمة الجهاز **معرّفًا عشوائيًا في
`chrome.storage.local`** داخل الإضافة. ذلك كان كافيًا لتفعيل تجريبي، ولا
يصلح هوية نهائية للمنتج:

- **المثبَّت لا يستطيع قراءتها.** تخزين الإضافة معزول عن نظام الملفات
  بحكم تصميم المتصفح، فلا سبيل آمنًا لتسليمها إلى خدمة ويندوز.
- **تموت بموت الملف الشخصي.** إعادة تثبيت المتصفح أو ملف تعريف آخر يولّد
  هوية جديدة لجهاز لم يتغيّر.
- **يملكها المتصفح لا الجهاز.** والاشتراك يُباع للجهاز.

**البديل:** الإضافة لم تعد تملك هوية الجهاز إطلاقًا. تحمل **رمز تركيب
لمرة واحدة** قصير العمر، تسلّمه إلى الـRuntime بعد التثبيت، ويولّد
الـRuntime هويته بنفسه على الجهاز ويستبدل الرمز بتفعيل.

## ٢. الأطراف الأربعة

```
┌────────────────────┐        ┌──────────────────────────────────────┐
│  إضافة المتصفح      │        │  Backend المستضاف (مستوى التحكّم)     │
│  ──────────────    │        │  ─────────────────────────────────  │
│  • دخول            │───────▶│  • Supabase (service_role)          │
│  • حالة الاشتراك    │  HTTPS │  • إصدار رموز التركيب                │
│  • رمز تركيب واحد   │        │  • توقيع روابط Azure SAS             │
│  • تنزيل المثبّت    │        │  • تفعيل الجهاز الواحد               │
└────────┬───────────┘        └───────────────┬──────────────────────┘
         │ 127.0.0.1 (الرمز مرة واحدة)         │ HTTPS
         ▼                                     ▼
┌────────────────────────────────────┐   ┌──────────────────┐
│  GovMind Runtime (جهاز العميل)      │   │  Azure Blob      │
│  ─────────────────────────────    │   │  ──────────      │
│  • هوية الجهاز (DPAPI)             │──▶│  • المثبّت        │
│  • تنزيل المودل والتحقق منه        │SAS│  • ملف المودل     │
│  • إدارة llama-server              │   └──────────────────┘
│  • واجهة GovMind الثابتة           │
│  • API محلي على 127.0.0.1 فقط      │
└────────────────────────────────────┘
```

## ٣. حدود الثقة والأسرار

| السرّ | مكانه الوحيد | لا يوجد في |
|---|---|---|
| `SUPABASE_SERVICE_ROLE_KEY` | Backend المستضاف | الـRuntime، الواجهة، الإضافة، المثبّت |
| `AZURE_STORAGE_CONNECTION_STRING` | Backend المستضاف | كل ما عداه |
| `DEVICE_HASH_PEPPER` | Backend المستضاف | كل ما عداه |
| `SUPABASE_JWT_SECRET` | Backend المستضاف | كل ما عداه |
| `SUPABASE_URL` + `SUPABASE_ANON_KEY` | عام — يجوز في الواجهة | (ليسا سرًّا) |
| رمز التركيب (خام) | ذاكرة الإضافة، لدقائق | القاعدة (تجزئته فقط) |
| سرّ الجهاز (خام) | ملف على الجهاز محميّ بـDPAPI | القاعدة (تجزئته فقط)، السجلّات |

**قاعدة واحدة تحكم الجدول:** كل ما يمنح صلاحية على بيانات جهة أخرى يبقى
على السيرفر. الـRuntime برنامج على جهاز عميل — يجب افتراض أن العميل يستطيع
قراءة كل بايت فيه.

### ٣-١ لماذا لا يتحدّث الـRuntime إلى Supabase مباشرة

قد يبدو منطقيًا أن يقرأ الـRuntime اشتراكه من Supabase بمفتاح `anon` ورمز
مستخدم. لكن الـRuntime **لا يملك رمز مستخدم**: المستخدم سجّل دخوله في
الإضافة لا في الخدمة. وإعطاء الـRuntime رمزًا طويل العمر يعيد المشكلة
نفسها. لذلك يتحدّث الـRuntime إلى Backend GovMind وحده، ويصادِق بسرّ
جهازه — وهو سرّ **لا يفتح شيئًا** غير اشتراك هذا الجهاز.

## ٤. مسار التفعيل — رمز لمرة واحدة

```
الإضافة                     Backend                     Runtime
   │                           │                           │
   │ ① POST installation-session                           │
   │──────────────────────────▶│                           │
   │   (رمز المستخدم)          │ يولّد رمزًا عشوائيًا ٣٢ بايت  │
   │◀──────────────────────────│ ويخزّن SHA-256 له فقط       │
   │   الرمز الخام (مرة واحدة)  │                           │
   │                           │                           │
   │ ② تنزيل المثبّت (SAS)      │                           │
   │ ③ المستخدم يفتح المثبّت يدويًا ويوافق على UAC            │
   │                           │                           │
   │ ④ استطلاع 127.0.0.1/health                            │
   │──────────────────────────────────────────────────────▶│
   │◀──────────────────────────────────────────────────────│
   │ ⑤ POST 127.0.0.1/activate {token}                     │
   │──────────────────────────────────────────────────────▶│
   │                           │      ⑥ يولّد سرّ الجهاز      │
   │                           │◀──────────────────────────│
   │                           │  POST runtime/activate    │
   │                           │  {token, device_secret}   │
   │                           │                           │
   │                           │ ⑦ RPC ذرّي في PostgreSQL:  │
   │                           │   • استهلاك الرمز          │
   │                           │   • إنشاء تفعيل الجهاز     │
   │                           │──────────────────────────▶│
   │◀──────────────────────────────────────────────────────│
   │ ⑧ تُمحى نسخة الإضافة من الرمز فورًا                      │
```

**لماذا RPC واحد في القاعدة (⑦)؟** لأن «استهلاك الرمز» و«إنشاء التفعيل»
يجب أن ينجحا معًا أو يفشلا معًا. عبر PostgREST لا توجد معاملة تمتدّ عبر
طلبين، فطلبان متتاليان يتركان نافذة: رمز استُهلك بلا تفعيل (يفقد العميل
تركيبه)، أو تفعيل بلا استهلاك (يُعاد استعمال الرمز). دالة
`redeem_installation_session` تفعل الاثنين في جملة واحدة.

### ٤-١ ما الذي يفشل، وكيف

| الحالة | أين تُرفض | النتيجة |
|---|---|---|
| رمز خاطئ | لا صف بهذه التجزئة | ٤٠١ |
| رمز منتهٍ | `expires_at <= now()` في شرط الـRPC | ٤٠١ |
| رمز مستعمَل | `used_at is not null` في شرط الـRPC | ٤٠١ |
| إعادة إرسال الرمز نفسه | الشرط نفسه — الصف صار مستعمَلًا | ٤٠١ |
| جهاز ثانٍ | **فهرس فريد جزئي في القاعدة** | ٤٠٩ |
| اشتراك منتهٍ | فحص الحالة قبل الاستهلاك | ٤٠٣ |

الجهاز الثاني يُرفض في القاعدة لا في بايثون: طلبان متزامنان ينجح أحدهما
ويفشل الآخر بـ`23505` مهما كان توقيتهما.

## ٥. هوية الجهاز على ويندوز

**سرّ عشوائي ٣٢ بايت** يولّده الـRuntime عند أول إقلاع بـ`secrets.token_bytes`.

**لا يُشتقّ من عتاد.** عنوان MAC واسم المستخدم ورقم القرص كلها إمّا غير
مستقرة (تتغيّر ببطاقة شبكة أو محاكاة) أو قابلة للانتحال أو تكشف هوية
المستخدم. سرّ عشوائي مخزَّن **يخصّ التثبيت** ويصف ما نريد وصفه بالضبط:
«هذا التركيب على هذا الجهاز».

**الحماية:** DPAPI بنطاق `LOCAL_MACHINE` عبر `CryptProtectData` في
`crypt32.dll` بـ`ctypes` — لا حزمة إضافية. مع `entropy` ثابت للتطبيق، فلا
يفكّه برنامج آخر بمجرد استدعاء DPAPI على الملف.

> **حدّ يجب ذكره صراحة:** DPAPI بنطاق الجهاز يحمي من نسخ الملف إلى **جهاز
> آخر**، ولا يحمي من مستخدم إداري على **الجهاز نفسه**. لا يوجد على ويندوز
> بلا عتاد TPM مخصّص ما يمنع مالك الجهاز من قراءة سرّ يستعمله برنامجه هو.
> هذا حدّ معماري لا عيب تنفيذ، وسياسة «جهاز واحد» تبقى مفروضة في القاعدة.

### ٥-١ ماذا يحدث بعد…

| الحدث | السلوك | ما يحتاجه العميل |
|---|---|---|
| **إعادة تثبيت GovMind** | المثبّت يبقي `device.bin`، فيبقى التفعيل | لا شيء |
| **إلغاء التثبيت ثم التثبيت** | يُحذف السرّ، فيلزم رمز تركيب جديد | إعادة الخطوات من الإضافة — والتفعيل القديم يجب أن **يُبطَل** أولًا |
| **إعادة تثبيت ويندوز** | مفاتيح DPAPI تُفقد، فالسرّ غير قابل للفكّ | إبطال من المسؤول ثم تفعيل جديد |
| **تغيير الجهاز** | الجهاز الجديد بلا سرّ | إبطال من المسؤول ثم تفعيل جديد |
| **إبطال المسؤول للتفعيل** | أول تحديث استحقاق يفشل بـ٤٠٣ فيتوقف المودل | تفعيل جديد من الإضافة |

`device.bin` تالف أو غير قابل للفكّ يُعامَل كغيابه: الـRuntime يطلب تفعيلًا
جديدًا بدل أن يعمل بهوية مجهولة.

## ٦. عمليات الـRuntime

عمليتان لا أكثر:

1. **`govmind-runtime.exe`** — العملية الرئيسية. تحمل API المحلي، وتخدم
   واجهة GovMind الثابتة، وتشرف على العملية الثانية.
2. **`llama-server.exe`** — عملية ابنة يبدأها الـRuntime ويوقفها معه.

**الإشراف:** يُبدأ `llama-server` بمنفذ حرّ على `127.0.0.1`، ويُنتظر حتى
يستجيب `/health`، ولا يُعلن GovMind جاهزًا قبل ذلك. عند الإيقاف تُنهى
العملية الابنة أولًا، ولا تبقى عملية يتيمة تحجز ذاكرة وملفًا.

**بلا نافذة طرفية:** كلتاهما تُشغَّلان بـ`CREATE_NO_WINDOW`.

### ٦-١ المنافذ

| الخدمة | العنوان | الوصول |
|---|---|---|
| API الـRuntime + الواجهة | `127.0.0.1:8765` (أو أول منفذ حرّ) | loopback فقط |
| `llama-server` | `127.0.0.1:<عشوائي>` | loopback فقط، **لا يُعلن ولا يُوثَّق للعميل** |

**لا شيء يُربط بـ`0.0.0.0`.** ولا يُكشف مسار OpenAI عام: مسارات المحادثة
في الـRuntime محميّة برمز محلي، فلا يستطيع موقع ويب مفتوح في المتصفح نفسه
أن يستهلك المودل.

### ٦-٢ المصادقة المحلية

يولّد الـRuntime عند كل إقلاع **رمز جلسة محلي** يكتبه في ملف داخل مجلد
البيانات. الواجهة تقرأه من مسار محلي (`/api/local/session`) المسموح لأصل
`127.0.0.1` وحده، وترسله في كل طلب.

المسار الوحيد **بلا** رمز محلي هو `/health` — تحتاجه الإضافة قبل أن تملك
شيئًا، وهو لا يكشف إلا «هل الـRuntime يعمل ومرحلته الحالية».

## ٧. المودل: تنزيل وتحقق

| الشرط | التنفيذ |
|---|---|
| لا يُحزَم داخل المثبّت | مدوّنة Azure منفصلة (`AZURE_MODEL_BLOB_NAME`) |
| استئناف | `Range` + ملف `.part` يبقى بين المحاولات |
| حجم متوقّع | `AZURE_MODEL_SIZE_BYTES` يُقارَن قبل التحقق |
| سلامة | `AZURE_MODEL_SHA256` يُحسب على الملف كاملًا |
| لا تثبيت ناقص | التسمية إلى `.gguf` **بعد** نجاح الحجم والتجزئة |
| مساحة القرص | تُفحص قبل البدء، مع هامش |
| الرابط لا يُعرض ولا يُحفظ | يُطلب عند الحاجة ويُستهلك فورًا |

ملف `.part` بحجم خاطئ أو تجزئة خاطئة **يُحذف**، ولا يُعامَل مودل غير
مُتحقَّق منه كمثبَّت أبدًا.

## ٨. واجهة GovMind

الواجهة الحالية (Next.js) كلها صفحات عميل: لا مسارات API ولا middleware،
وكل مساراتها الخمسة تُولَّد ساكنة. لذلك تُصدَّر بـ`output: "export"` إلى
ملفات ثابتة **يخدمها الـRuntime نفسه**.

**النتيجة: لا Node.js ولا Python على جهاز العميل.** المثبّت يحمل
`govmind-runtime.exe` (بايثون مجمّعة داخله) وملفات الواجهة الثابتة
وثنائيات llama.cpp.

الاختصار يفتح المتصفح على العنوان المحلي، فلا يكتب العميل عنوانًا.

## ٩. ما يبقى من المرحلة الأولى بلا تغيير

- مزود LM Studio **باقٍ** كما هو (`MODEL_PROVIDER=lmstudio`) — للتطوير.
- مزوّد جديد `llamacpp` يتحدّث إلى `llama-server` المُشرَف عليه.
- تعليمات النظام وسياق المحادثة ومصادر RAG وتجريد المزوّد: تُستعمل كما هي.
- Oracle ومخزن الذاكرة و Supabase: ثلاثتها باقية.

---

## ١٠. ما لا يفعله هذا التصميم

- **لا يُخفي UAC ولا SmartScreen.** المثبّت غير موقّع في هذه المرحلة،
  وويندوز سيقول «ناشر غير معروف». لا يُلتفّ على ذلك.
- **لا يُشغّل المثبّت تلقائيًا** من الإضافة.
- **لا يطلب من العميل نسخ رمز أو رابط أو بصمة** يدويًا.
- **لا يدّعي جاهزية للإنتاج** قبل شهادة توقيع.
